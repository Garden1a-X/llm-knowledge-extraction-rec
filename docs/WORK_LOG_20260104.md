## 💡 解决方案：Entity重分配（两阶段LLM）

### **核心思路**

在进行entity clustering之前，必须先确保relation边界清晰：
1. 先解决relation边界问题（重分配entities到正确的relation）
2. 再解决entity命名问题（聚类同义词/语义相近的entities）

### **方案设计（三阶段流程）**

```
Phase 2b-0: Entity Redistribution（实体重分配）
  ├─ Stage 0: 人工定义14+1个relation的职责边界 ✅
  │   └─ 输出：RELATION_DEFINITIONS.md
  │
  ├─ Stage 1: Filtering（筛选 - 逐个relation处理）⬅️ 当前进行中
  │   ├─ 对每个relation独立判断：哪些entities真正属于该relation
  │   ├─ 输入：Relation定义 + 该relation下的所有entities
  │   ├─ 处理：逐个entity调用LLM（CoT推理）
  │   │   └─ 先分析特征（entity_meaning, key_features, exclusion_check）
  │   │   └─ 再判断归属（belongs: true/false + suggested_relation）
  │   ├─ 输出：entity_redistribution_stage1_filtering.json
  │   │   └─ keep列表 + remove列表（每个remove都有suggested_relation）
  │   └─ 脚本：scripts/phase2b_stage1_filtering.py
  │
  ├─ Stage 1.5: Redistribution（重新分配 - 全局处理）⬅️ 待实现
  │   ├─ 收集所有relations的remove列表
  │   ├─ 根据suggested_relation重新分配entities
  │   ├─ 处理冲突：
  │   │   └─ entity在A被移除→建议去B，同时在B被移除→建议去C
  │   │   └─ 决策逻辑：投票机制 / 优先级规则 / 人工审核
  │   ├─ 输出：entity_redistribution_stage1_5_reallocation.json
  │   │   └─ 每个relation的最终entity列表（keep + 接收的entities）
  │   └─ 脚本：scripts/phase2b_stage1_5_redistribution.py（待实现）
  │
  └─ Stage 2: Merging（合并同义词 - 逐个relation处理）
      ├─ 对每个relation内部识别并合并同义词
      ├─ 输入：Stage 1.5重分配后的entity列表
      ├─ 输出：entity_redistribution_stage2_merged.json
      └─ 脚本：scripts/phase2b_stage2_merging.py

Phase 2b-1: Entity Clustering（实体聚类）
  ├─ 基于Phase 2b-0清理后的数据
  ├─ 跨relation的语义聚类（可能合并相似entities）
  └─ 压缩目标：626 → 250-270个标准entities
```

### **关键决策**

经过讨论，用户做出以下决策：

**1. depicted_subject vs character_type**：保留两个，严格区分
- `depicted_subject`：画面主要视觉主体（人物基础类型、物体、场景）
- `character_type`：人物的角色类型、职业、关系（仅限人物相关）
- 理由：主体可能是建筑物（纪录片、灾难片）、特殊物品，不一定是角色

**2. visual_theme**：保留，但严格重定义
- 定位：叙事主题/概念主题/视觉概念
- 剔除：单纯颜色 → color_palette，单纯情绪 → mood，艺术流派 → artistic_styles
- 保留：war, romance(主题), urban_life, nostalgia, minimalism(概念)

**3. color_palette范围**：接受单一颜色
- 单一颜色（red, blue）也算color_palette
- 理由：单一颜色放visual_theme更奇怪

**4. depicted_entities合并**：合并到depicted_subject
- 理由：数据量太少（6个entities），且语义重叠

**5. action_behaviors**：暂时保留
- 虽然稀疏，但先观察重分配后的情况

**6. 第一轮是否做entity合并**：是
- 理由：反正要call LLM，GPT-4应该能同时做好剔除和合并
- 目标：减少总entity数量，节约成本

## 💭 重要洞察

### **为什么必须先做entity重分配？**

1. **聚类的前提是同质性**：
   - 如果一个relation下的entities主题混杂（如visual_theme混了颜色+情绪+风格）
   - 聚类算法会混淆，无法收敛到语义一致的clusters

2. **减少后续成本**：
   - 现在用LLM清理一次entity分布，后续entity聚类会更准确
   - 如果直接聚类，会产生大量语义不一致的clusters，需要更多人工干预

3. **提升最终质量**：
   - 确保每个relation下的entities都是该relation职责范围内的
   - 最终的知识图谱会更加清晰、可解释

### **LLM vs 人工清理**

**为什么选择LLM？**
- 626个entities人工审核太慢
- LLM擅长语义分类和同义词识别
- 可以并行处理（第二轮重分配）

**LLM的局限性**：
- 边界模糊cases可能判断错误（如"romantic" vs "romance"）
- 需要非常清晰的prompt和边界规则
- 需要人工审核高频entities的变动
