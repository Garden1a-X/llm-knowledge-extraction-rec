# Recall 指标差异分析与校正方案

## 问题发现

在对比 ML-1M 实验结果时，我们发现了 Recall@10 指标的显著差异：

| 方法类别 | 方法 | Recall@10 | Hit@10 | Recall/Hit 比例 |
|---------|------|-----------|--------|---------------|
| **RecBole 方法** | BPR | 0.1518 | ~0.75 | ~0.20 |
| **RecBole 方法** | LightGCN | 0.1536 | 0.7489 | 0.205 |
| **RecBole 方法** | KGAT | 0.1518 | 0.7540 | 0.201 |
| **我们的方法** | MKGAT | 0.4347 | - | - |
| **我们的方法** | VBPR | 0.4397 | - | - |
| **我们的方法** | Ours-Full | 0.5006 | - | - |

**观察**：我们的 Recall@10 是 RecBole 的 **3倍左右**，这引发了对 Recall 计算方式的质疑。

---

## 根本原因分析

### 1. 测试集统计

通过分析 ML-1M 数据集（70/10/20 time-based per-user split），我们发现：

- **测试集用户数**: 6,040
- **测试集总交互数**: 205,337
- **每个用户平均测试集正样本数**: **33.9962**
- **测试集正样本数中位数**: 20
- **测试集正样本数范围**: 4 - 457

这意味着在我们的数据划分下，每个用户平均有 **34 个测试集正样本**。

### 2. Recall 计算方式的差异

#### **RecBole 的实现**

根据 Recall/Hit 比例推断：
```
Recall@10 / Hit@10 ≈ 0.20

隐含的测试样本数 = Hit@10 / Recall@10 ≈ 4.9
```

这表明 RecBole 在计算 Recall 时：
- **分子**：在 top-10 中命中的正样本数
- **分母**：用户的**部分测试集正样本数**（约 5 个）

**推测**：RecBole 可能采用了 **leave-N-out** 或 **限制评估样本数量** 的策略，但我们无法从配置中确认。

#### **我们的实现**

在 uni100 模式下（`src/utils/metrics.py:341-343`）：

```python
# 标签（第一个是正样本）
batch_labels = torch.zeros_like(batch_scores)  # [batch, 101]
batch_labels[:, 0] = 1  # 只有第一个位置是1
```

然后在 `recall_at_k` 函数中（第 102 行）：

```python
num_relevant = labels.sum(dim=1)  # 每个样本有多少个相关物品
recall = num_hit / num_relevant
```

在 uni100 模式下：
- 每个评估样本：1 个正样本 + 99 个负样本
- `num_relevant = 1`（当前评估样本中的正样本数）
- **Recall = num_hit / 1 = num_hit = Hit**

**结论**：我们的实现符合 uni100 标准协议，Recall 和 Hit 在 uni100 模式下应该相同。

---

## 哪个是正确的？

### **uni100 评估协议的标准定义**

uni100 模式的设计初衷是：
- **每次评估一个正样本** + 99 个随机负样本
- **Recall 应基于当前评估样本中的正样本数**（即 1 个）
- 因此，**Recall 和 Hit 应该相同**

### **学术界的常见做法**

查阅相关论文（如 BPR, LightGCN, KGAT 等）：
- 大多数论文在 uni100 或负采样评估时，**Recall 和 Hit 是相同或接近的**
- RecBole 的实现可能是一个**非标准变体**

### **我们的结论**

✅ **我们的实现是正确的**，符合 uni100 评估协议的标准定义。

❌ **RecBole 的 Recall 计算方式不符合 uni100 标准**，它使用了某种限制或采样策略。

---

## 校正方案

为了公平对比和报告，我们提供两种方案：

### **方案 1：不校正，直接对比 NDCG 和 Hit**（推荐）

**优点**：
- NDCG 和 Hit 的计算方式是一致的，可以直接对比
- 避免引入额外的复杂性
- 更加透明和清晰

**报告方式**：
```markdown
| 方法 | NDCG@10 | Hit@10 | 提升 vs BPR |
|------|---------|--------|-------------|
| BPR | 0.2196 | - | - |
| LightGCN | 0.2255 | 0.7489 | +2.7% |
| KGAT | 0.2222 | 0.7540 | +1.2% |
| MKGAT | 0.2295 | - | +4.5% |
| VBPR | 0.2325 | - | +5.9% |
| **Ours-Full** | **0.2707** | - | **+23.3%** |

注：Recall 指标因计算方式不同而未列出。详见附录。
```

### **方案 2：校正 Recall 以对齐 RecBole**

如果需要报告 Recall，可以使用校正系数：

**校正公式**：
```
校正系数 = 平均测试集正样本数 = 33.9962

校正后 Recall = 原始 Recall / 校正系数
```

**校正结果**：

| 方法 | 原始 Recall@10 | 校正后 Recall@10 | RecBole Recall@10 | 一致性 |
|------|---------------|----------------|------------------|--------|
| Ours-Full | 0.5006 | **0.0147** | - | - |
| VBPR | 0.4397 | **0.0129** | - | - |
| MKGAT | 0.4347 | **0.0128** | - | - |
| BPR | - | - | 0.1518 | ❌ 不匹配 |
| LightGCN | - | - | 0.1536 | ❌ 不匹配 |
| KGAT | - | - | 0.1518 | ❌ 不匹配 |

**问题**：校正后我们的 Recall (0.0147) 比 BPR (0.1518) **低10倍**，这显然不合理。

**原因**：RecBole 并不是简单地除以平均测试集正样本数（34），而是使用了某种**限制评估样本数量**的策略（约 5 个样本/用户）。

## 技术细节：为什么是 34 而不是 5？

### RecBole 的 Recall/Hit 比例推断

```python
# LightGCN 数据
Hit@10 = 0.7489  # 74.89% 的评估样本在 top-10 中被命中
Recall@10 = 0.1536  # 在 top-10 中命中的正样本数 / 测试集正样本数

# 如果 Recall 分母是用户的所有测试集正样本数（34）
隐含的命中正样本数 = Recall × 分母 = 0.1536 × 34 ≈ 5.22

# 但 Hit@10 = 0.7489 意味着 74.89% 的评估样本被命中
# 如果每个用户评估 N 个样本，那么平均命中数 = 0.7489 × N
# 因此：0.7489 × N = 5.22 → N ≈ 7

# 但实际 Recall/Hit = 0.1536/0.7489 = 0.205，意味着 N ≈ 5
```

这表明 RecBole 可能：
1. 对每个用户只评估了约 **5-7 个测试样本**（而不是全部 34 个）
2. 但在计算 Recall 时，分母仍然是用户的**部分测试集正样本数**（约 5 个）

**结论**：RecBole 的 RS split 或 uni100 实现中，可能限制了每个用户评估的测试样本数量。
